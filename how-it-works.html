How this is actually built

Not a generic description — this is the real pipeline, with the actual numbers, including the parts that don't work perfectly. 1

Brief

Every lesson starts with a written dedup note, not just a title

Before any writing happens, each lesson's brief spells out exactly what the immediately preceding lesson already covered and what this one must not repeat — by name, by formula, by example. This is the single mechanism keeping 284 (or 184) lessons from ever re-teaching each other.

Real example: RAG Atlas's lesson on distance functions was explicitly told to reuse the exact same three example vectors its previous lesson (cosine similarity) had already used — on purpose, to prove that raw distance and cosine similarity disagree on ranking until the vectors are normalized. Nothing about that connection was invented after the fact; it was in the brief before a single line was written.
Newer optimization — a running ledger: checking for repeats used to mean re-reading the entire previous lesson every time. A compact ledger file now holds a short summary of every lesson built so far, in both courses — the dedup check now runs against that full history in one pass, not just the single lesson immediately before it.
2

Research & verify

This is the slow part, and it's slow on purpose

Before writing a word, the agent reads the previous lesson in full (the dedup check above), reads the site's lesson-template spec, and finds 2–4 external references — then verifies every single one with a live HTTP request before it's allowed into the text. A reference that can't be fetched and confirmed doesn't get cited, full stop.

  • Every numeric example gets independently recomputed before it's written into a lesson — not trusted from memory, run through an actual calculation.
  • Every external link gets curled and grep-checked against its own title tag, not assumed to still be live.
Why it takes so long: this is a live network call plus hand-verifying every formula, every time — for every single lesson. It's the reason a single concept can take 15–30 minutes even when nothing goes wrong.
Newer optimization — a reference cache: the same sources (a Wikipedia page, a library's docs) get cited across many lessons. A shared cache now remembers which URLs were already verified and when — a repeat citation skips the network call entirely instead of re-checking a page that was already confirmed live days earlier.
3

Write

A fixed template, filled in fresh every time

Every lesson follows the same shape: a short guided "beginner core" (10 steps) and a much longer optional "advanced deep dive" (24 sections), plus one genuinely new interactive lab widget — never copy-pasted from an earlier lesson's lab, even when the underlying idea is related.

4

Self-check

The lesson has to pass its own structural exam

Before anything is considered finished: every HTML tag has to balance, every required section ID has to appear exactly once, and the lab's JavaScript has to parse cleanly. This catches malformed pages before they ever reach the site.

5

Re-link the site

The previous lesson gets edited too, not just the new one

Finishing a lesson means going back and flipping the previous one's status from "active" to "complete," bumping the module's progress counter, and updating the homepage's "what's active right now" summary — three separate files touched by every single lesson.

A real bug this caused: one lesson got written directly in "complete" state by mistake — even though it was actually the newest, still-active lesson — because that text gets copy-adjusted from the previous lesson's own already-complete blocks. Caught by checking for exactly this contradiction (a lesson marked complete with no later lesson yet built) and fixed by hand.
6

Checkpoint

A small log file records progress in three stages

Started researching, started writing, finished — three check-ins per lesson into a shared log file, which is what lets this dashboard show something close to live status.

7

Batch & orchestrate

2–4 lessons per unattended run, then the repo gets pushed once per module

An orchestration layer runs a short queue of these agents, one at a time, as a single background job. When a batch finishes, the next one gets queued automatically. A course's public repo only gets pushed once a full module — 8 to 12 lessons — is completely done, so the commit history reads as real milestones, not noise.

When it breaks — the honest numbers

This isn't a hypothetical caveat. Here's what's actually happened across recent batches.

~40%

Of the lessons attempted in the last several batches needed a manual finish — not because the research was wrong, but because the run got cut off after finishing all its verification, and sometimes even writing the interactive lab's code, just before writing the actual lesson page. When that happens, the already-verified research and code get reused directly rather than redone — only the missing piece gets hand-written.

1 strike

The retry policy (tightened from an earlier 2-attempts/20-minute rule): if a lesson's first attempt fails, or makes zero forward progress for 15 minutes, the automatic retries stop immediately and a person finishes it by hand — a second automated attempt was rarely doing any better anyway, so it stopped being worth the wait.

3+

Separate times the three-stage checkpoint log (stage 6 above) has silently lost an entry — a lesson built perfectly and shipped, but its own "finished" check-in never got written, leaving a gap in this dashboard's history. The module/lesson counters shown on the main page don't have this problem — they're read directly from the real, on-disk build state, not from this log — so the gap is cosmetic, not a sign the lesson is missing.

What it's actually built with
Plain HTML / CSS / vanilla JS — no build step, no framework Git + GitHub for version control GitHub Pages for hosting, all three sites GitHub REST API for the Q&A channel Live curl checks to verify every external reference Node.js for structural self-checks (tag balance, syntax) A Windows scheduled task + PowerShell for syncing this dashboard's data
This is a person-directed build: the course structure, module ordering, dedup rules, quality bar, and every published lesson are reviewed and decided by a human, with AI coding agents doing the drafting, reference-checking, and self-testing legwork against a fairly detailed brief per lesson. Estimates on the main status page are approximate, not a live billing meter.
