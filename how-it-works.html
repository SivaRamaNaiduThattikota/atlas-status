How this is actually built

RAG Atlas and ML Atlas are two from-scratch course sites, built one lesson at a time. This page is the honest version of "what's going on behind the progress bar" — the process, the tooling, and the rough edges.

Scale

Two courses, both concept-by-concept

284RAG Atlas concepts, 24 modules
184ML Atlas concepts, 20 modules

Every concept is its own standalone lesson page: a static HTML file, a short JS file for a hands-on interactive lab, and a shared stylesheet. Nothing is templated at runtime — each lesson is a real, finished file sitting in the repo.

The build unit

One AI coding agent per concept

Each lesson is produced by a single autonomous coding agent given a detailed, concept-specific brief: the exact title, which module it belongs to, and — critically — a written note describing exactly what the previous concept already covered and what this one must not repeat.

Per concept, that agent is instructed to:

  1. Read the site's lesson-template spec and the immediately preceding lesson in full, as both a style guide and a duplicate-content check.
  2. Find 2–4 candidate external references (papers, docs) and independently verify each one with a live HTTP request before citing it — no reference gets included on trust alone.
  3. Write the lesson into the site's fixed template: a short guided "beginner core" followed by an optional, much longer advanced deep dive.
  4. Design and build one genuinely new interactive lab widget in plain JavaScript — never reused wholesale from an earlier concept.
  5. Hand-verify any numeric worked example with an independent calculation before it's allowed into the lesson text.
  6. Self-check the HTML: every tag balanced, every required section present exactly once, the JS parses cleanly.
  7. Flip the previous lesson's status to "complete," bump the course's progress counter, and update the homepage's "what's active right now" summary.

Why sequential, never parallel

Concept 2 cannot start until Concept 1 is really on disk

Concepts are built strictly one after another, never concurrently. The dedup/continuity check in step 1 above only works if the previous lesson is already finished and readable — running several concepts at once would mean each one is guessing at content that might change underneath it. Slower, but it's the only way to guarantee nothing gets taught twice and nothing contradicts an earlier lesson.

Orchestration

Batches, not one giant run

An orchestration layer runs a short, fixed pipeline of these builder agents — typically 3–4 concepts per batch — entirely unattended once launched. Each batch is its own background job; when one finishes, the next batch for that course is queued automatically rather than waiting to be manually restarted.

A course's repo is pushed to its public GitHub Pages site once a full module (roughly 8–12 concepts) is complete — not after every single concept — so the commit history reads as real milestones rather than noise.

Being honest about the tracking

The progress log is good, but not perfect

Each agent is also asked to check in to a small progress-tracking file at three points — starting research, starting to write, and finishing — so this dashboard can show something close to live status. In practice, that check-in step is the least reliable part of the whole pipeline: an agent occasionally skips it under time pressure even though the actual lesson gets built perfectly fine. When that happens, the live "researching now / writing now" line on the dashboard is designed to just go quiet rather than show a stale status — the module/concept counters above it are the ones actually derived from the real, on-disk build state, so they stay trustworthy even when the finer-grained log has a gap.

When an agent gets stuck

Two strikes, then a person finishes it by hand

If the same concept fails twice in a row, or a single attempt makes no forward progress for 20 minutes, the automated retry stops. Whatever research, references, or partial files that stuck attempt already produced get reused directly — nothing is thrown away and redone from scratch — and a person manually writes whatever's left (usually just the final HTML file) using that same verified material.

This dashboard

A small companion site, watching the other two

This status page is its own separate, static site. It polls each course's progress file and a running cost-estimate log to draw the bars and numbers above, refreshes on a short interval, and shows exactly how stale its own data is (page-load time vs. when the underlying files were actually last synced) rather than pretending to be perfectly live.

It also carries a small two-way channel: the "Ask a question" box on the main page opens a pre-filled GitHub Issue on this dashboard's own repo. That's checked on a fast poll (every couple of minutes) — a question gets read, answered directly (sometimes by editing this very site), the issue gets closed, and the answer gets logged back onto the dashboard for anyone else to see.

What it's actually built with

No frameworks, nothing fancy

Plain HTML / CSS / vanilla JS — no build step, no framework Git + GitHub for version control GitHub Pages for hosting, all three sites GitHub REST API for the Q&A channel Live curl checks to verify every external reference Node.js for structural self-checks (tag balance, syntax) A Windows scheduled task + PowerShell for syncing this dashboard's data
This is a person-directed build: the course structure, module ordering, dedup rules, quality bar, and every published lesson are reviewed and decided by a human, with AI coding agents doing the drafting, reference-checking, and self-testing legwork against a fairly detailed brief per concept. Estimates on the main status page are approximate, not a live billing meter.
